# ScripticX — security hardening report

Updated: 5 August 2026

## Result

The issues from the initial audit now have code and database remediations in the repository. The database part is intentionally versioned in `supabase/migrations/20260805_security_hardening.sql`; it must be applied to the production Supabase project in the same deployment as the application changes.

## Fixed

### Authoritative scoring and rewards

- Problem code is evaluated by `POST /api/submissions/evaluate`, not trusted from the browser.
- The endpoint authenticates the bearer token, loads private test configuration with the service role, enforces code/test/output limits and computes the score on the server.
- The server creates the submission and derives a daily bonus from the active `daily_challenges` row. The client can no longer supply a trusted score or bonus.
- Direct browser writes to `submissions` and `daily_challenge_completions` are revoked by the migration.
- `role`, `banned`, `total_score`, `reward_points` and `equipped_rewards` are protected by column grants and a database trigger.

### RLS and authorization

- Explicit RLS policies are installed for the legacy public tables that were reported by Supabase Advisor: profiles, problems, submissions, classes and their membership/session/assignment tables, live rooms/messages/participants, follows, posts/comments/likes, notifications, certificates, snippets, contact messages and daily challenge tables.
- Existing unversioned policies on these tables are dropped first so a permissive old policy cannot be OR-combined with the new rules.
- Class creation and joining use security-definer RPCs that derive the user from `auth.uid()` and generate server-side invite codes.
- Admin role/ban changes use an admin-checked RPC. `RouteGuard` remains a UX layer only; authorization is enforced by RLS/RPC/API.
- Live-room code updates use a membership-checked RPC. Live rooms are readable only by their owner or invited/accepted participants.
- Public submission history no longer grants access to submitted source code.

### Notifications

- Browser code no longer inserts notifications directly.
- `POST /api/notifications` derives `actor_id` from the authenticated session and validates every supported event against its actual follow, post, comment, assignment, group or live-room row.
- Titles, bodies and internal hrefs are generated by the server. Event keys prevent duplicate delivery and rate limiting limits spam.
- RLS permits recipients to read notifications and update only `read_at`; inserts are revoked from browser roles.

### Contact and uploads

- The contact form uses a server endpoint with strict field/body limits, server-side validation and a persistent 5/hour rate limit keyed by authenticated user or hashed IP.
- Storage buckets enforce file-size and MIME allowlists. Paths for avatars and post images are owner-scoped; badge and shop assets are admin-only.
- SVG uploads for public shop assets are disabled. PNG, JPEG and WebP remain supported; this removes the frontend-only SVG sanitizer bypass.
- Client checks mirror the bucket limits for clearer feedback: avatar/banner 5 MB, post image 8 MB, badge icon 1 MB, reward/group media 5 MB.

### Browser and dependency hardening

- A Content Security Policy is sent with anti-framing, no object embedding, same-origin base/forms, explicit Supabase HTTP/WebSocket and YouTube/Monaco-compatible sources.
- HSTS, `nosniff`, Referrer Policy, Permissions Policy and disabled `X-Powered-By` are enabled.
- Next.js is upgraded from 15.5.18 to 16.3.0 because the current audit database also reports vulnerable PostCSS/Sharp chains in the 15.x line.
- Supabase/`ws`, Monaco/DOMPurify and all other resolvable transitive advisories were upgraded or overridden safely.
- Final result: `npm audit --omit=dev` reports **0 vulnerabilities**.

## Deployment order

1. Apply all Supabase migrations through `20260805_security_hardening.sql`.
2. Deploy the Next.js application and new environment-backed API routes.
3. Refresh Supabase Security Advisor; the RLS-disabled findings for the covered legacy tables should be gone.
4. Smoke-test with four accounts/roles: anonymous, student, teacher and platform admin.

Do not deploy only the frontend half: the new endpoints depend on the rate-limit function and RPCs in the migration, while the database revocations depend on the new endpoints.

## Verification performed

- `npm run typecheck` — passed.
- `npm run test:run` — 81/81 tests passed.
- `npm run build` — production build passed on Next.js 16.3.0.
- `npm audit --omit=dev` — 0 vulnerabilities.
- Local production smoke test confirmed CSP/security headers and a `401` response for an unauthenticated submission attempt.

## Remaining operational hardening

- Historical scores and wallet balances are not silently reset. New rewards require a `server-v1` verification marker, but any balance already inflated before this fix should be reviewed and reconciled once against trusted event/submission data.
- The MiniScript evaluator has strict step, input, test and output limits, but a separate worker/process sandbox would add another isolation boundary if arbitrary-language execution becomes more complex.
- CSP currently retains `unsafe-inline` and `unsafe-eval` for Next.js/Monaco compatibility. A nonce-based CSP can remove these after a dedicated browser compatibility pass.
- Rate limiting is database-backed. At substantially higher traffic, move it to an edge/KV limiter and add automated cleanup/retention for old rate-limit keys.
